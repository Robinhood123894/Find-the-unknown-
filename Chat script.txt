Deep Understanding of the Problem


1. What the Problem Actually Is (The Core Insight)


This is not an Al problem at its core. It is a forensic data-audit problem where Al is a tool for interpreting messy, multi-modal evidence (PDFs, images, logs, JSON, SQLite dumps) and reconstructing ground truth. The real difficulty is reconstructing state across systems and time, then applying a deterministic policy engine to decide what should exist vs. what does exist.


The "Al-powered" framing is a trap. The hidden canonical answers almost certainly generated by a deterministic reference implementation over structured evidence. If you build a pure LLM pipeline, you will lose on ordering, evidence_id citation, and exact operation names. You need hybrid: Al for extraction/normalization, deterministic logic for decisions, ordering, and serialization.


Let me break it down properly.

Hidden answers are canonical generated by reference code, not by a model. Exact operation names, states, ordering, and evidence citations are graded. LLMs are unreliable at strict ordering and exhaustive enumeration.

This is the crux. Draw a hard line.


AI IS USED-3 touchpoints only


Touchpoint 1-Vision extraction (PDFs, images).


When: a file in dataset/evidence is a scanned PDF or image.


What: extract structured Record/Activity JSON matching our pydantic schema.


Model: one multimodal model, temperature 0, JSON mode.


Guard: output re-validated by pydantic; failures retried once; then flagged.


Cached by file sha256 never re-called.


Touchpoint 2-Ambiguous log line interpretation.


When: a log line doesn't match any deterministic regex parser.


What: classify into [event type, system id, resource_id, user_ref, ts).


Model: cheap text LLM, temperature 0, few-shot with 3-5 examples.


Guard: result must map to a known system id and event enum, else dropped.


Cached by line hash; batched (many lines per call to save tokens).


Touchpoint 3-LLM Verifier (the Option D layer).


When: after deterministic steps are built, per case (or sampled).


What: audit the compact case bundle and return (missed: [...], invalid: [...]]


Model: mid-tier text LLM, temperature 0, strict JSON.


Guard: verifier never writes steps json. Each "missed item triggers a deterministic re-evaluation of the policy engine for that record; each "invalid" citation is deterministically re-resolved or dropped.


Bounded: 2 retries per case, full audit log.


XAI IS FORBIDDEN - everything else


These are pure code, and this is where grading accuracy lives:


1. Identity resolution/historical identifier graph-BFS+ fixpoint. No LLM.


2. Timeline replay/state-at-audit derivation-state machine. No LL.M.


3. Applying deletion_rules.csv dict lookup. No LL.M.


Status decision (COMPLETE/INCOMPLETE/NOT_APPLICABLE) - decision function. No LLM.


Exception: the NOT APPLICABLE classifier on request text may use Touchpoint-2-style LLM as a fallback only when rules are unsure. Primary path is rule-based.


5. Step construction, ordering, ranking, step no assignment-code. No LLM.


6. evidence id resolution code (file_id/activity_id/audit_id lookup). No LLM-generated IDs ever.


7. Final JSON serialization & CSV writing-code. No LLM.


The One-Line Rule


Al turns unstructured bytes into structured data. Code turns structured data into graded


decisions and JSON. The LLM never sees deletion_rules.csv and never emits a step object.


That line is what protects you on sequence accuracy, evidence citations, and exhaustiveness.
